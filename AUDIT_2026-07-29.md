# secondbarnone — codebase, game, and production-health audit

**Audit date:** 29 July 2026  
**Audited revision:** `7f18e8599bdecfbcb2346277d164aa2b80a53588`  
**Scope:** the current checkout, including the shipped `docs/` site, source art, scripts, tests, CI configuration and documentation. This is a static/code and headless-play audit; it is **not** a substitute for a real-device usability or human playtest.

## Executive assessment

`secondbarnone` has a notably good *foundation* for a small browser game: it is a simple static deployment; the simulation rules are separated from the DOM; the content catalogues are data-driven; weather and daily variance are deterministic; and the project has unusually extensive catalogue tests. The game also has a clear, attractive premise and a strong amount of character-facing content for its scale.

It is **not release-healthy as checked in today**. The actual CI installation cannot begin, the declared asset budget fails by a wide margin, a complete dependency-installed test run fails, formatting is not clean, and the balance simulator demonstrates that a simple preview-reading strategy cannot lose. Several documents and handoff notes describe an earlier state rather than this revision. The result is a project that looks healthier from its README than it is when verified from a clean checkout.

## 1. What the project actually is today

The shipped game is a vanilla ES-module static web application. `docs/` is both source and deployment directory for GitHub Pages; `docs/js/main.js` only boots `initGame()`, `app.js` wires screens and persistence, `core/` owns simulation rules, `data/` owns catalogues, and `ui/screens.js` constructs the UI. There are no runtime third-party scripts or network calls. This is an appropriate technology choice for the game: it makes local hosting and deployment simple and avoids a build pipeline for what is roughly 5,000 lines of game JavaScript.

The actual catalogue is:

- **23 locations** across five districts (not 22 as most player-facing documents say).
- **78 characters:** 1 protagonist, 1 arch-nemesis, 2 rivals, and 74 side characters.
- **235 location-bound, character-bound events**; all 78 characters own events.
- 9 weather types, 10 perks costing 66 insight in total, 9 festivals, and **20 achievements** (not the 22 claimed in some documentation).
- A day-60 soft win, plus an unpresented day-100 mastery check.

The hub shows the two founding locations plus four deterministic slot-based choices. The map renderer still exists, but it is not reachable from the player UI: `renderHub()` accepts `onMap` but never renders a City/Map button. This is corroborated by the current ESLint warning that `onMap` is assigned but unused. `api.goto.map()` remains available only to tests/the console. This matters because the balance simulator selects from **all unlocked locations**, whereas the player normally chooses from the six cards currently offered.

### Architectural strengths worth retaining

1. **Clean simulation boundary.** `GameState`, `resolveTurn`, `EventManager`, data catalogues and deterministic RNG can run under Node without a browser. This is why the project can test whole-world invariants rather than just examples.
2. **Deterministic information.** Weather and location variance are hashes of day/seed, so forecast, card preview and resolution can agree. That is a player-respecting solution to variance.
3. **Content relationships are encoded, not merely documented.** Tests ensure hosts have locations, events point to real characters and their location, ids are unique, unlock rules work, and every portrait/background exists.
4. **Small, safe browser surface.** The UI mainly uses `textContent` and DOM construction. The one `innerHTML` capability in the `el()` helper has no current callers. No account system or remote service means local-save tampering is a product choice, not a security incident.
5. **Good art delivery concept.** 288px inline WebP portraits and 896px on-demand lightbox portraits are a sensible two-tier model; all 78 portrait masters are square PNGs of at least 1024px.

## 2. Verification results and release integrity

### Commands run

| Check | Result | Interpretation |
| --- | --- | --- |
| `git fsck --full --no-reflogs` | Pass | No local object corruption found. |
| `git diff --check HEAD` before this audit document | Pass | No pre-existing whitespace errors. |
| `npm ci --ignore-scripts` | **Fail** | Lockfile is out of sync with `package.json`. |
| Bare `npm test` without installed dev dependencies | Misleading pass: 282 passed, 85 skipped | jsdom suites skip when `jsdom` is absent, so this does not validate the UI. |
| Full `npm test` after a temporary local `npm install` | **366 passed, 1 failed, 0 skipped** in ~103 seconds | The real suite is not green. |
| `npm run lint` after temporary install | Exit 0 with 2 warnings | Unused `MONEY_SOFT_CAP` and `onMap`. Warnings are not treated as failures. |
| `npm run format:check` after temporary install | **Fail** | 15 source/CSS/HTML files do not conform to the committed Prettier configuration. |
| `npm run typecheck` | False green | `tsc` is not installed; the script catches that error and echoes success. |
| `node scripts/check-assets.js` | **Fail** | 3 asset-budget failures. |
| `npm audit` after temporary install | 0 known vulnerabilities | Positive, but not a reproducible current-checkout result until the lockfile is fixed. |

### P0: dependency lock and CI are broken

`package.json` declares `jsdom`, `eslint`, and `prettier`, while `package-lock.json` only records `jsdom` at its root. As a result, the committed `.github/workflows/check.yml` fails at `npm ci` before tests, assets or coverage run. A normal `npm install` repairs the lockfile with a roughly 1,072-line lockfile diff, but that repair is not committed.

This is the first thing to repair: regenerate and commit the lockfile from the intended Node version, add an `engines` field (Node 22 is used in CI), and verify the workflow in GitHub Actions. Do not describe CI as active/green until an actual Actions run succeeds.

### P0: the shipped asset budget is failing

`node scripts/check-assets.js` reports:

```text
assets/music/warm_piano.wav is 6460 KB (limit 400 KB)
eager payload: 10.22 MB (limit 4.00 MB)
lightbox tier: 6.08 MB
total payload: 16.30 MB (limit 8.00 MB)
```

The 75-second uncompressed WAV accounts for 6.46 MB by itself. It has `preload="auto"` in `docs/index.html`, but no application code ever retrieves the audio element or calls `play()`. In practical terms, the player pays the load cost without receiving sound; autoplay policies would also prevent silent automatic playback from being reliable.

Choose one coherent outcome:

- remove the unused audio now; or
- encode a short loop as Opus/AAC, load it only after an explicit user sound toggle, expose controls and persisted preference, then set a revised measured budget.

The current asset test is doing its job; its thresholds should not be raised merely to make the build green.

### P0: full tests reveal a real specification conflict

With jsdom installed, `tests/ui.test.js` fails *“a day-one storm keeps the woods shut even for Brian.”* That test expects the House of Middleway welcome to respect a storm closure. In contrast, `evaluateUnlock()` explicitly returns the day-one welcome before inspecting closed weather tags, and `tests/world.test.js` explicitly asserts that the welcome **overrides** weather closures.

This is not a flaky test; it is two incompatible product decisions. Decide which player experience is intended, update the model/UI/tests/comments together, and make the whole suite mandatory. At present the missing-dependency skip hides this contradiction on a bare checkout.

### Quality gates need to be honest

- The typecheck command must install `typescript` and fail when `tsc` fails, or be removed. `|| echo 'Type check completed'` turns a missing tool into a green check.
- Make jsdom a required dev dependency in practice, not an optional test dependency. CI should run the UI tests and fail if it cannot.
- Add `--max-warnings 0` if lint cleanliness is a release expectation.
- Put lint and formatting checks in CI; the current workflow only runs tests, assets and coverage.
- The UI test suite still hardcodes 480ms transition sleeps and 2.8-second toast sleeps. The complete run took roughly 103 seconds. Make fade/toast durations injectable at boot and use zero in tests; then share a common jsdom harness.

## 3. Gameplay and systemic-design review

### What works

The core fantasy is readable in one sentence: trade money, sanity and energy while maintaining a community and working in a bar. The daily preview is particularly good: the exact deterministic location result, weather, festival and perk adjustments are visible before commitment. This makes a potentially opaque five-resource system planable.

The city is also structurally better than a random event pool. Every location has a host; events are tied to somebody and their place; the character screen provides biography and relationships without overloading the location screen. This supports a sense of place and gives the large cast a defensible purpose.

The fixed hub slots are a smart UI rule. They preserve muscle memory while allowing the city to rotate. Weather gates, festivals, a capped recent history, and a non-prescriptive daily nudge fit the desired calm tone.

### The balance is not currently delivering the advertised dilemma

The existing `scripts/simulate.js --runs=100 --days=200` drives the real turn resolver. Its current output is stark:

| Strategy | Deaths | Mean final day | Mean money | Mean sanity | Top choices |
| --- | ---: | ---: | ---: | ---: | --- |
| Random | 42% | 123 | 346 | 97 | broadly distributed |
| Alternate founding pair | **100%** | 24 | 15 | 5 | 50% bar / 50% community |
| Greedy preview reader | **0%** | 200 | 231 | 100 | Home Loft 38%, Bathhouse 23%, Farmers’ Market 13% |

I also repeated the greedy probe using only the six cards offered by the actual hub rather than all unlocked locations: it still produced **0 deaths in 100 seeded 200-day runs**, with 100 soft wins. The probe favors Home Loft (18.2%), Bathhouse (15.3%), Farmers’ Market (9.1%), Night Market (8.1%) and Radio Station (7.2%). This is not a substitute for human testing, but it is strong evidence that reading previews makes survival deterministic rather than tense.

The issue is not that skilled play succeeds; it is that the stated central bar/community trade becomes bad content. A player following the advertised two-location loop dies every time around day 24, while a very simple weighted heuristic can bank money, cap sanity and reputation, and accumulate large amounts of unused insight.

**Recommendations:**

1. Retune from a written target, such as: a thoughtful player reaches day 60 reliably but still faces meaningful risk; random play fails often; a greedy strategy survives frequently but not indefinitely; and the founding loop is viable without being dominant.
2. Make rest economically meaningful. Home Loft and Bathhouse are repeatedly selected because they repair energy while having tolerable opportunity cost. Test consecutive-rest patterns and their opportunity cost explicitly.
3. Add a late-game sink or conversion. At day 200 the greedy simulation ends with money, maxed reputation and 81 unspent insight; the hub-limited probe ends with even more insight. Ten perks cost only 66, reputation caps at 100, and static 18-money rent stops creating pressure.
4. Preserve event unpredictability without relying on it as the only threat. The weighted event mean is positive sanity (+2.28), essentially neutral money (-0.01), slightly negative energy (-0.65), and positive reputation/insight. This makes events flavor-forward rather than an economy sink, which is fine if the location/rent economy carries the tension.
5. Put survival-band assertions around a *UI-legal* choice pool in the committed simulator. The existing simulator’s full-unlocked pool is useful, but not a direct model of what the current hidden-map UI presents.

### The simulator itself needs correction

The simulator output labels `goalRate` as `day-100`, but it checks `GameState.won`, which is awarded at **day 60**. Its loop stops when `journeyDay < maxDays`, so a `--days=60` simulation stops before it can award the day-60 win. Rename the metric, correct the horizon boundary, and record strategy assumptions in the report. Otherwise, balance data will mislead future tuning.

### Content breadth exceeds run exposure

Events are scheduled every 2–5 days. Before the day-60 goal, a run can see only about 11–29 scheduled events before location/weather gates reduce that further. That means only a small slice of a 235-event catalogue can be experienced per completed run. The volume is excellent as a replayability reservoir, but it does not by itself create a coherent character arc in a single journey.

Consider selecting a smaller set of recurring, stateful character beats for each run, while retaining the larger pool as ambient variation. A compact “what changed” marker in People would make an arc legible without reinstating a full journal.

### Feature promises that are not implemented end-to-end

- **The City/map route is dead.** The renderer and app callback are present, but no hub control calls it. Either expose it, or remove the code and make the six-card constraint an intentional documented rule.
- **The mountain retreat’s “Three days, counted as one” is text only.** `special: 'long_trip'` renders a note; turn resolution always advances one day and has no long-trip rule. The fiction, calendar and mechanics disagree.
- **The day-100 mastery win is invisible and non-idempotent.** `checkSecondWin()` emits every qualifying turn, does not persist a separate mastery flag, and overwrites `winMessage`. `resolveTurn()` returns `masteryWon`, but `app.js` and `renderResultModal()` do not display it. Either build a real one-shot second ending/achievement or remove the dormant feature until it has UX.
- **Rent prepayment has an exploitable Sunday path.** `prepayRent()` sets `rentPrepaidUntilDay = max(previous, journeyDay) + 7`. Prepaying at the letting office on Sunday suppresses rent for both that Sunday and the next Sunday with one payment. The office unlocks after day 5, so this is reachable on day 11 and later. Anchor from `journeyDay - 1` when rent is currently due (or forbid prepayment on a due Sunday) and add a regression test.
- **One turn can resolve twice at the model layer.** Calling `resolveTurn()` twice before `advanceDay()` applies two days’ effects on the same calendar day. The visible button disables itself, but a central simulation invariant belongs in the model/state and must be saved. Add a per-day resolution guard, reject duplicate calls explicitly, and test it.

## 4. Code integrity and persistence

### State/persistence strengths

Game state is JSON-serializable, clamps resources, handles calendar rollover, version-migrates v3 saves to v4, and uses failure-tolerant `localStorage` calls. These are good choices for a client-only game.

### Persistence gaps

`GameState` is saved, but `EventManager` is not. Reloading a run creates and initializes a fresh event manager, which changes the scheduled next event, loses recent-event memory, and reseeds event randomness. Weather and location variance remain deterministic, but event cadence/repeat behavior does not survive a reload. Save the event scheduler state (`nextEventDay`, recent ids and seeded RNG state), or deliberately state that event timing is regenerated and remove the deterministic-play claim from surrounding material.

Save loading is intentionally tolerant, but trusts several loose values: achievement ids and visited-location ids are not filtered against their catalogues; calendar fields are independently clamped rather than made mutually valid; and a malformed local save can retain impossible combinations. This is not a security concern for a single-player local game, but a validation/sanity pass will reduce corrupted-run support burden.

### Legacy and dead paths

The current source still contains paths that handoff material says were removed:

- `applyLocationAction`, `applyEventDeltas`, `LOCATION_COPY`, `_previousEventId`, and `_lastRentDayOfMonth` are retained largely for tests/back-compat in a self-contained static game.
- `scripts/generate-avatars.js` (612 lines) is still called by `optimize-assets.sh` despite all characters having painted portraits.
- `scripts/process-portrait.sh` still emits the deprecated one-tier 512px deployment asset, conflicting with the 288/896 portrait builder.

Either document an external compatibility consumer or delete these paths and retarget tests to current behavior. Keeping test-only legacy code inflates coverage and complicates future maintenance.

## 5. UX and accessibility review

The baseline is above average for a small web game: buttons are semantic, resource gauges use `role="meter"`, keyboard focus styling is visible, portrait images have useful alt text, dynamic toast status is announced, and reduced-motion CSS/particle behavior exists. Text-based deltas and explanations reduce dependence on color alone.

The highest-value UX/accessibility fixes are:

1. **Do not let a backdrop click commit a day.** The day-result backdrop calls `onContinue()` when the player clicks outside the dialog. That removes the result and advances time. A stray mobile tap should not make a consequential choice; require the Continue button.
2. **Finish modal dialog behavior.** The result modal declares `role="dialog" aria-modal="true"` but has no Escape behavior, focus trap or focus restoration. The portrait lightbox is treated more carefully. Reuse the lightbox dialog pattern or a small shared modal controller.
3. **Give dynamic avatars intrinsic dimensions.** The HUD image has width/height, but portraits created by `avatar()` do not. Add known dimensions to reduce cumulative layout shift.
4. **Provide sound intentionally or remove it.** A hidden, unplayable preloaded audio file is neither accessible nor useful.
5. **Run real browser/device checks.** jsdom cannot validate touch target size, actual image loading, contrast on bright backgrounds, font/layout overflow at 320px, or keyboard focus return. Test at 320px, 768px and desktop with keyboard and screen-reader smoke passes.

## 6. Art, payload, and presentation

### Current visual read

The sampled environments and portraits have a coherent warm, painterly Paris-adjacent look. The strongest assets establish lived-in interiors and a calm, cinematic palette; the separate portrait tiers are visibly appropriate for small avatar and enlarged-art use. The non-human characters are represented as distinct objects/creatures rather than being silently humanized, which is a positive consistency pass.

The art is not yet standardized enough to be called a finished production pipeline:

- Deployed backgrounds range from 960×536 to 1376×768 despite the stated 1000px convention.
- The visual direction is mostly warm, bright/high-key interiors and painterly scenes; a final human art-direction pass should check readability under text overlays and ensure outdoor/night settings retain distinct moods rather than collapsing into the same amber palette.
- The current roadmap honestly identifies all but Brian as AI-generated/unverified in origin. Keep that provenance clear internally and obtain human editorial/cultural review for narrative and visual representation before marketing “custom” or “painted” work.

### The art documentation contradicts itself

`docs/ART_STANDARDIZATION_SPEC.md` opens with “no baked frames” as the v2.0 policy, while later “mandatory” composition and prompt sections still demand a circular distressed frame. The actual assets mostly follow the newer frame-less direction, with Brian and Vanna as intended exceptions. Consolidate the spec to one rule and one prompt before the next batch; otherwise regeneration will reintroduce the style inconsistency the policy was meant to remove.

### Repository-health cost

The deployed `docs/` tree is 16.32 MiB, source masters are 231.46 MiB, and the local Git object store is about 303 MiB. Sixty-four source assets exceed 2 MiB. The current checkout is shallow and exposes only two reachable commits, so historical diagnosis is limited here even if the remote has more history.

Keep the optimized deployed WebPs in the game repository. Move full-resolution masters to Git LFS or a versioned external art archive with a documented fetch/build step, then perform a deliberate history rewrite only with repository-owner approval. This will materially improve clone time and contributor onboarding.

Finally, `docs/` deploys internal art reports/specifications (`ART_*`, `PORTRAIT_REFERENCE.md`, `side_characters_report.md`) as public Pages files. Move internal working notes to `notes/` and retain only intentional player-facing files under `docs/`.

## 7. Documentation health

Documentation is plentiful but currently cannot be trusted as a single source of truth. Examples:

- README and PROJECT_OVERVIEW repeatedly say **22** locations; code has **23**.
- README says 22 achievements; code has 20.
- README/overview say 360 tests; current Node reports 367 test entries. The full suite has one failure.
- HANDOFF says 64 events, 293 tests, v3.0.0, dead code/scripts removed, faster tests, fixed prepay exploit, and CI not active. The current code has 235 events, v2.2.0, legacy scripts/code present, slow tests, the prepay exploit, and an active-but-broken workflow.
- DESIGN_REVIEW and old assessment material describe earlier content counts and decisions.

After fixing P0, appoint `README.md` as the concise player/developer truth, generate catalogue counts in a small script where possible, archive dated audits/handoffs rather than editing them as current status, and eliminate duplicated art-status files.

## 8. Prioritized recovery plan

### P0 — make the repository verifiably releasable

1. Regenerate/commit `package-lock.json`; add Node engine support; run the actual GitHub Actions workflow.
2. Remove or properly implement/compress/lazy-load the 6.46 MB WAV. Keep asset budgets enforced and make `node scripts/check-assets.js` pass.
3. Resolve the Brian/storm product decision and make the full jsdom suite green with no skips in CI.
4. Fix Sunday rent prepayment and add a regression test.
5. Correct the typecheck script or remove the false-success quality gate.

### P1 — repair game-system integrity

6. Add a model-level “one resolved turn per journey day” guard, persist it, and test duplicate resolution.
7. Decide whether the City map is a real player feature. Expose it with a clear hub button or delete it and revise simulator assumptions.
8. Retune energy/rest/rent/perks against versioned, UI-legal balance simulations. Add survival, resource-sink and founding-loop assertions.
9. Fix the simulator’s day-60/day-100 label and horizon boundary.
10. Persist event-scheduler/RNG state or explicitly redesign reload behavior.
11. Implement or remove the day-100 mastery endpoint and make mountain-trip time mechanically real if the text promises it.

### P2 — improve sustainable quality

12. Remove legacy/test-only APIs and superseded image scripts; make the portrait builder the sole art output route.
13. Make formatting clean, elevate lint warnings, factor test timing/harnesses, and reduce full-suite runtime.
14. Consolidate the art specification, move internal docs out of `docs/`, and update all catalogue/version counts.
15. Move master art to LFS/external archive, then schedule a deliberate repository-history cleanup.
16. Complete real-device accessibility and human balance playtests before calling the game production-ready.

## Bottom line

The project is much closer to a strong, maintainable game than a typical prototype because its core rules and content are organized and testable. The immediate task is not a rewrite: it is to restore truthfulness between the repository, its checks, and its design claims. Once the install/asset/test blockers are fixed, the most valuable product work is a focused balance pass around rest, rent, the founding loop and late-game sinks, followed by real human/device testing. That sequence preserves the codebase’s best qualities while turning the current attractive prototype into a reliable release candidate.
