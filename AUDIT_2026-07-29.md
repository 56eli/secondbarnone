# secondbarnone — full game audit & development recommendations

**Audit date:** 29 July 2026
**Branch:** `arena/019faeaf-secondbarnone` (HEAD `ef9d1e3` — merge of PR #34)
**Scope:** shipped `docs/` game, source art, scripts, tests, CI, UX/A11y, balance, narrative/content, and long-term maintainability. This is a static/code + headless-simulation audit; it is *not* a substitute for a real-device usability pass or a human playtest panel.

---

## 0. Executive summary

`secondbarnone` is a short, hand-crafted narrative resource-management game about Léon, who splits days between a spiritual community and a bar while keeping sanity, money, energy, reputation and insight alive across a Paris-shaped city of 23 locations and 78 characters.

The codebase is in **better shape than a typical small-team web game** — static ES modules, a deterministically seeded simulation, a clean rules/UI split, 371 headless + jsdom tests at ~99.5% line coverage, passing lint + prettier + asset budget out of the box, and a content catalogue (locations, characters, events, perks, weather, festivals, achievements) that is data-driven and structurally validated. `npm ci && npm test && node scripts/check-assets.js && npm run coverage:check` all pass today on a clean checkout with Node 22.

That is the good news. The game's **design and end-state still have real issues** that a test suite and code coverage cannot catch:

1. The core advertised loop ("community restores sanity / bar pays the bills") is **not the winning strategy** when the rest of the city is unlocked.
2. Events are net-positive on average, which makes the event layer mostly flavour rather than tension.
3. The "three-day mountain retreat" and the "day-100 mastery ending" exist in text/data but **not in mechanics or UX**.
4. Event-scheduler state does not survive save/load, breaking the deterministic-play promise.
5. Rent prepayment on a Sunday still gives you a free week.
6. The day-result modal can be dismissed (and time advanced) by a stray backdrop click; Escape does not close it; there is no focus trap.
7. Balance, content discovery, and late-game pressure need a deliberate pass before the game can be called "release-ready" rather than "charming and mostly functional."

The path to release is **not a rewrite**. It is a focused sequence of small fixes to mechanical integrity, then one balance pass, then one UX pass, then content-polish. A concrete prioritized list is in §8.

## 3. Code architecture

### What is working well
- **Pure simulation.** `GameState`, `resolveTurn`, `EventManager`, variance, and weather all run under Node without a DOM. This is why catalogue invariants, balance simulations and 99% coverage are achievable.
- **Deterministic information.** Weather and per-location variance are hashed from `(journeyDay, runSeed)`, so hub previews and actual resolution agree — a player-respecting design that removes "the card lied" frustration.
- **Data, not code.** Locations, characters, events, perks, weather, festivals and achievements are each a single data module. Adding content rarely requires touching engine code.
- **Safe DOM construction.** The `el()` helper builds nodes imperatively and only has an `html` escape hatch that no current caller uses; XSS risk is essentially nil and user input is limited to save data from `localStorage`.
- **Two-tier art delivery.** 288 px WebP inline portraits + lazy 896 px hi-res sheets (only fetched when tapped) is a strong, mobile-friendly trade-off.
- **Failure-tolerant storage.** `saveStore` catches every `localStorage` error; private-mode and quota failures do not crash the game.

### Things to improve
- **`app.js` owns too much of the modal lifecycle.** The result modal is appended to `<body>` by `app.js` after calling `renderResultModal` from `screens.js`, while the portrait lightbox manages its own body-appending and focus/Escape/restore behavior in `screens.js`. One shared modal controller would fix several A11y issues at once (see §6).
- **Stat constants are re-exported through two files.** `core/balance.js` defines them and `core/game-state.js` re-exports them. This works but leaves comments and defaults in two places. Small cleanup.
- **Legacy shims accumulate.** `applyLocationAction`, `applyEventDeltas`, `LOCATION_COPY`, the two-stat `SANITY_GAIN/MONEY_GAIN/SANITY_LOSS/MONEY_LOSS` constants, and `_lastRentJourneyDay` are kept "for tests/back-compat." They should either have a documented external consumer or be removed in a single cleanup PR so coverage reflects real code.
- **`MONEY_SOFT_CAP` is exported from `game-state.js` but never imported in non-test code** (ESLint currently reports this, which means lint is configured not to warn on unused exports — worth tightening).
- **`scripts/generate-avatars.js` and `scripts/process-portrait.sh`** reference an older generated-avatar pipeline that is contradicted by the current painted-portrait policy. They still exist and are called from `optimize-assets.sh`; they should either be the canonical path again or be deleted.

## 4. Gameplay & balance

### 4a. The simulation, honestly

I re-ran the committed simulator at 200 seeds × 200 days:

| Strategy | Death rate | Death cause | Reaches day 60 ("win") | Mean survival | Mean end-state |
| --- | ---: | --- | ---: | ---: | --- |
| Random (distracted player) | **92%** | money 182 / sanity 2 | 8% | 53 d | mon 9 / san 97 / rep 55 / ins 43 |
| Alternate (founding loop: bar when money ≤ sanity, else community) | **38%** | money 32 / sanity 44 | 62% | 142 d | mon 68 / san 63 / rep 86 / ins 74 |
| Greedy (reads previews, weights low resources, buys perks) | **18%** | money 35 / sanity 0 | 82% | 195 d | mon 47 / san 99 / rep 100 / ins 303 |

The greedy strategy's top destinations are Home Loft (28%), Temple Ruins (15%), Farmers' Market (10%), Night Market (8%), Sato's Studio (8%), Mountain Retreat (6%) — not the bar/community founding pair. It never visits Free Clinic or the Landlord Office.

I also ran a **hub-faithful** version of greedy that chooses from exactly the six cards the UI actually offers (2 founding + 4 rotating deterministic slots), rather than from every unlocked location:

| Variant | Death rate | Day-60 rate |
| --- | ---: | ---: |
| Greedy, all unlocked | 18% | 82% |
| **Greedy, hub-limited** | **20%** (all money deaths) | **80%** |

Two conclusions:

1. The UI's 6-card constraint doesn't create meaningful additional pressure on top of the preview-reading strategy — it just changes which rest/money places are preferred.
2. The player-facing pitch ("the community restores your sanity but costs money; the bar pays but grinds you down; rent hits every Sunday; reach day 60") is only partially honest. **The founding pair is a trap you are meant to outgrow** (alternating them dies 38% of the time), and the real winning play is rotating into rest/insight/rep locations early. That is actually a richer game, but the early text doesn't prepare the player for it.

### 4b. Why greedy is too safe

- **Home Loft (+2 sanity / −6 money / +30 energy, variance ±6 energy) is overpowered for its unlock state.** It is slot 3, available from day 1, and restores more energy than two nights of sleep at the cost of a cheap food day. It is the greedy AI's #1 pick because it pays for itself in one or two bar shifts.
- **Rest compounds cheaply.** Energy recovery is 14/night; Home Loft + a single bar night nets +10 energy before perks and variance. The player never actually has to live in the "week to recover" band the design promises.
- **Bathhouse** (slot 3, unlocks day 9: +6 / −10 / +22) and **Temple Ruins** (slot 4, day 12 rep 30: +22 / −8 / −26) similarly refill sanity and energy faster than work drains them once perks land.
- **Events are net-positive.** Across the 235-event pool, average per-event deltas are: **+3.3 sanity / +1.2 money / −0.4 energy / +1.0 reputation / +0.7 insight.** The hurtful tail is small (9 `rare_hurtful` vs 67 `rare_helpful`), and the `Thick Skin` / `Long View` perks dampen and amplify respectively, so late-game events are a cushion, not a threat.
- **Reputation caps at 100, Insight piles up past any sink.** The greedy sim ends runs with ~303 insight unspent and a full reputation bar. Total cost of every perk is 66 insight; after that, insight-generating actions have no marginal value.
- **Rent plateaus at 42** minus reputation discounts of 1–2, and `Tenants' Union` cuts it another 5 for a floor of 35/week. By day 48 (one escalation step after the early game), rent is essentially flat for the rest of the run while income keeps growing.

### 4c. Concrete balance recommendations

These are tuning suggestions, not mandates — pick bands and sim-assert them (the `tests/balance.test.js` harness is exactly the right tool).

1. **Make rest cost real opportunity.**
   - Home Loft: drop energy from +30 to about **+20**, raise money cost to **−8** (a day of doing nothing still costs rent-proportional food).
   - Bathhouse: drop energy from +22 to **+16**.
   - Add a "you can't rest two days running and feel good about it" friction — e.g., repeated REST locations within 3 days apply a small sanity penalty from guilt/lost momentum.
2. **Nerf the highest-sanity/insight payouts.** Temple Ruins +22 sanity and Mountain Retreat +32 sanity both refill ~25%+ of the sanity bar in one day; bring them closer to +15 / +22 respectively so they remain a treat, not a reset button.
3. **Sharpen rent scaling.** Consider a second escalation slope after day 75 (or removing the 42 cap and replacing it with a gentler logarithmic curve), and apply reputation discounts only to the first X rent (e.g., via a `community_fund` perk, not passive).
4. **Add a late-game insight sink.** The simplest is an **offering/renovation track** at La Maison Calme: spend 30→60→100 insight for a cosmetic + persistent small bonus (or even just for flavour/ending variants) once the 10-perk tree is bought out.
5. **Make events a slight net-negative economy on average.** Target means of roughly: sanity ~+0.5, money ~−1, energy ~−1, reputation ~+0.5, insight ~+0.5. Re-weight `rare_hurtful` up to ~20–25 events (currently 9) so surprises actually threaten a run.
6. **Re-balance the founding pair to be viable-but-not-dominant.** Alternating bar/community should survive ~65–75% of runs to day 60, not 62%, and *with* the other locations the good player should reach ~75–85% wins, not 82% deaths-only-from-money.
7. **Tighten the preview.** The chip preview shows *exact* deterministic numbers, which is what makes greedy-AI-perfect play possible. Two light options:
   - Show ranges ("Sanity +1 to +4") instead of exact numbers, while keeping variance deterministic under the hood. The player can learn places without getting a spreadsheet.
   - Keep exact previews but add a ~10% chance of a small hidden event or "the day took an unexpected turn" drift that the preview cannot show — use sparingly so trust is preserved.
   I would lean toward (a) — it is honest while not being a solve.

### 4d. Mechanical bugs / promises the game doesn't keep

These are more important than tuning.

- **Rent prepayment on a Sunday is still a free week.** `prepayRent()` sets `rentPrepaidUntilDay = max(previous, journeyDay − 1) + weeks × 7`. If `journeyDay` is a Sunday on which rent is due and not yet charged, `journeyDay − 1` is Saturday, so the prepaid window starts on the Saturday *before* today and today's rent is treated as already covered — you pay 18 to cover *next* Sunday, and today's 18 is silently skipped. This is reachable from day 11 (Landlord Office opens day 5). The function should anchor to `journeyDay` when rent is *not* due today, to `journeyDay + 6` when it is due today, or simply refuse prepayment on a rent-due Sunday. Add a regression test — the simulator should catch it once the fix makes greedy runs worse.
- **`checkSecondWin()` is not idempotent and is not surfaced.** It returns `true` every turn after day 100 (it never sets a flag like `checkWin()` does with `this.won`), it overwrites `winMessage`, and `renderResultModal` reads `result.masteryWon` but displays nothing distinct for it (it is folded into the same toast as the 60-day win). Three choices:
  - Build a proper one-shot second ending (a new modal, an achievement, a changed game-over title) and set `this.masteryWon = true` after firing once.
  - Or strip it until it has UX.
  Currently it's test-covered code that doesn't produce a player-facing payoff.
- **"Three days, counted as one" at the mountain retreat is just flavor text.** `special: 'long_trip'` renders a note; `resolveTurn` always advances one day and charges one day of variance. Either implement it (advance 2 extra days, apply rent twice, skip two events, make it clear in the preview chips) or change the copy to "a day trip" — the current text promises a mechanic the game does not deliver.
- **Event scheduler and RNG state are not persisted.** `EventManager` fields `_nextEventDay`, `_recentIds`, `_previousEventId`, and the seeded RNG's internal state are rebuilt fresh on load. After reload the next event fires on a different day than the player would have seen, and the "recent events won't repeat" memory resets. This contradicts the README's claim of deterministic play and matters psychologically — "I reloaded and the event changed" is a feel-bad in a narrative game. Add an `eventManager.toJSON()` / `loadFrom()` pair (and persist `rng.state()` for the seedable generator — mulberry32 state is just one integer) and save/load it alongside `GameState`.
- **The map/city route is dead.** `renderHub` accepts no `onMap` handler and `api.goto` has no `map` entry any more. The district constants exist but are unused in any player-facing UI. This is fine — the six-card rule is good — but remove the leftover references in comments so future contributors don't try to add a map button.

## 5. Content & narrative

### Strengths
- **235 events, 78 characters, every character has ≥3 events in their location.** This is an unusually large content surface for a 60-day game (a run sees roughly 12–25 scheduled events, so there is real replay value).
- **Host small-talk per character** is a lovely touch — every location has a quote that changes deterministically with journey day, giving a sense of recognition without heavy scripting.
- **Rivals/nemesis are present as locations** (Sato's Studio, Vermillion/Alex, Agence du Quartier/Kaden) and have multi-beat arcs that the test suite enforces.
- **Festivals** (9 total) are date-bound, not random — they anchor specific calendar moments the player can learn.
- **The day-one Brian welcome** is a great onboarding decision: it guarantees a friendly face on day 1 without making the chapel permanently easy.
- **Weather closes outdoor places** (storms, snow) and modifies others (rain helps quiet places; heat helps nights), which makes the forecast mechanically meaningful rather than cosmetic.

### Content issues
1. **Character arcs are not visible to the player.** Kaden/Sato/Alex have multi-beat events, but there is no "relationship" indicator, no journal entry, no "your history with X" pane on the People screen beyond the static bio. Adding a small **"where you left off"** line per character (state-machine driven, fed by arc-event flags) would turn a big event pool into actual stories.
2. **Runs see <15% of the event catalogue** before day 60. That is fine for replay, but a single journey can feel like "random things happened to random people." Pick ~8–12 characters per run as the *focused* cast (including rivals + a rotating handful) and weight their events up, while keeping the rest as ambient flavor. The People screen can mark focused people with a small "you've been getting to know X" cue.
3. **Event text is currently all "you" narration with no choices.** Adding lightweight choices on rare events (e.g., "take the tip / refuse it") with small stat trade-offs would give agency without turning the game into a full branching VN. The infrastructure already has deltas — it's just adding two `(text, deltas)` branches per chosen event.
4. **The two characters with "non-human" portraits** (Carl-bot, Cat, etc.) are charming — consider leaning further into that tonal flavour rather than letting it feel like in-repo jokes.
5. **Bios read as a single paragraph per character.** A short "first impression" / "after you've spent time there" toggle (unlocked by visiting the host's location N times) would add warmth with very little text.

### Narrative tone
The writing is strong — quiet, observational, gentle, specific to Paris-with-a-fictional-sheen, and it treats tiredness and money stress with sympathy rather than irony. That is the game's biggest differentiator and should be protected in any future content push. Add a short **WRITING_GUIDE.md** (500 words max) describing voice, tense, pronoun use, and which real-world references are in/out, so contributors (and AI-assisted drafts) stay on-model.

## 6. UX & accessibility

### Already strong
- Semantic `<button>` elements everywhere; no `<div onclick>` for controls.
- `role="meter"` with `aria-valuenow/min/max` on all stat bars.
- Visible focus rings in the CSS.
- `aria-selected` on the character list (listbox pattern).
- `role="dialog" aria-modal="true"` on portrait lightbox and result modal.
- `aria-live="polite"` toasts host.
- Portraits have `alt`, lazy load, decode async, draggable false.
- `prefers-reduced-motion` disables particles and the CSS already collapses motion.
- High-contrast mode is a persisted toggle.
- Result modal auto-focuses the Continue button; portrait lightbox auto-focuses the close button and restores previous focus on Escape; Escape closes the portrait lightbox.

### Gaps (fix in this order)

1. **Backdrop click on the result modal advances time.** `backdrop.addEventListener('click', e => { if (e.target === backdrop) onContinue(); })` means a stray tap on mobile, or a mis-click while reaching for the modal, dismisses the end-of-day report and **rolls the calendar forward**. This is a load-bearing action — it must require the Continue button. The portrait lightbox is correctly dismissible by backdrop click because closing it has no side effects. Remove the backdrop-click-continues behavior, or restrict it to right-click / no-op.
2. **Result modal has no Escape key, no focus trap, no focus restoration.** The portrait lightbox has all three. Refactor into a shared `openModal(node, { onClose })` helper and reuse it for both (and any future modal).
3. **Tab order can escape the modal.** When a modal is open, Tab still walks the hub/settings/buttons behind the backdrop. A small focus trap (loop Tab between first and last focusable child) fixes it.
4. **Touch targets.** Several `.btn-small` buttons (perks, hub tools) are ~28–32 px in CSS. WCAG 2.5.5 recommends 44×44 CSS pixels for interactive targets. Bump padding on mobile widths.
5. **Stat delta chips are color-only.** `.chip.pos` / `.chip.neg` currently use green/red; the `+`/`−` sign is present, which is good, but in high-contrast mode ensure both color and the sign/icon are always legible on the painted backgrounds.
6. **No audible feedback.** That is a *feature* per README ("No audio"), and removing the phantom WAV was the right call. If you add audio later, default to muted with a visible toggle, honor `prefers-reduced-motion` for sound, and preload nothing.
7. **The Settings screen is missing a New Run / Reset button and a "delete save" control.** Right now restart only happens after game over. A player who wants to abandon a run has to clear `localStorage` via devtools. Add an explicit "Abandon run" button behind a confirmation dialog.
8. **The almanac Energy Outlook is a static three-bucket string** (`Low` / `Moderate` / `Strong`) with no reasoning. It would be more useful if it showed "After today's previewed action you'd be at X% energy."
9. **The daily nudge is good but appears as an `<aside>` with no live-region announcement.** If the nudge is critical (low sanity + low money), announce it via the existing `aria-live` toasts host the first time it appears that day.
10. **Screen rotation / narrow mobile.** The six-card hub is a 3×2 grid. At 320 px wide (iPhone SE) the cards and chip rows are readable; I did not see a mobile viewport meta bug, but the text on `.choice-action` and `.choice-eff` wraps to 3–4 lines, which makes each card quite tall. A real-device pass is still worth doing (the README already admits this).

## 7. Art & payload

- **Eager payload 3.88 MB / 4 MB budget, total 9.76 MB / 10 MB.** Under budget, but tight; adding another location or a larger portrait could push the eager tier over. Keep check-assets in CI.
- **78 portraits, all with hi-res sheets present.** Two-tier delivery is working as intended.
- **Backgrounds** are WebP and look cohesive. A few are slightly off the documented 1000 px width (some 960, one 1376). This is cosmetic but a future re-encode pass should normalize to 1000×560.
- **Provenance.** README and notes are honest that most portraits are AI-generated and not all have been human-verified. Before marketing the game with words like "hand-painted" or "custom art," do a final editorial/cultural pass on all character bios and portraits — particularly the non-Western names and the "rival/nemesis" characters, who shoulder more of the story.
- **Source masters in `assets/` are 239 MB** and not shipped to GitHub Pages, which is correct. Long-term, move them to Git LFS or an external versioned art bucket; clone size will matter if more contributors join.
- **`docs/` currently contains no internal working notes** — that has been cleaned up since prior audits; keep it that way.

## 8. Prioritized plan (what to do next)

Ordered so the riskiest/most-visible fixes come first. Sizes are rough.

### P0 — mechanical integrity (0.5–1 day)
1. **Fix Sunday prepayment exploit.** Anchor `prepayRent()` correctly when rent is due today; add regression test; verify simulator results for the greedy strategy shift slightly but believably.
2. **Persist `EventManager` state (next event day, recent ids, RNG state) in the save.** Mulberry32 state is one 32-bit integer, so add a `state()`/`setState()` pair and serialize it.
3. **Idempotent day-100 mastery win.** Add a `masteryWon` flag (like `won`), fire once, either surface it in the result modal with a distinct message or strip the dead code path.
4. **Implement or retract the mountain-retreat three-day mechanic.** My recommendation: implement (advance 2 extra days, charge rent on schedule, note it on the preview chips). If you don't, change the location copy.
5. **Make backdrop click on the result modal not advance time.**

### P1 — UX / A11y sweep (1 day)
6. Extract a **shared modal controller** with: focus trap, Escape to cancel (with distinct semantics: lightbox dismisses without consequence; result modal still requires Continue), focus restoration, and body-scroll lock while open.
7. Add **Abandon Run** to Settings with a confirmation dialog; add it to the post-game-over screen as well.
8. Bump small-button hit targets to ≥44 px on touch widths.
9. Add lint (`eslint . --max-warnings 0`) and `prettier --check` to the GitHub Actions workflow.
10. Fix `npm run typecheck`: either add `typescript` as a devDependency and let it really fail, or remove the fake "Type check completed" echo.

### P2 — balance pass (1–2 days, with playtesting)
11. Apply the §4c tuning changes (rest costs, late-game insight sink, harsher events, rent scaling).
12. Add simulator **assertions** to `tests/balance.test.js`: random strategy <25% day-60 rate, alternate strategy 60–75%, greedy hub-limited 70–85%, mean end-game insight < 80 (forces a sink), no location >20% greedy pick rate.
13. Decide whether the preview chips should show exact numbers or ranges; implement one of the two consistently.
14. Re-run the simulator at 500 seeds after each tweak; don't ship a balance PR without posting the sim table on the PR description.

### P3 — content & narrative (3–7 days)
15. Add small **per-character state markers** on the People screen (e.g., "You've sat with Brian twice" / "Kaden is escalating") driven by events that fire. Even 2–3 states per rival/nemesis and host would make runs feel authored.
16. Add **lightweight choices** to 10–15 rare events for a sense of agency.
17. Add an **insight sink** (see §4c.4) once perks are bought out — renovating La Maison Calme, sponsoring a free clinic shift, etc. Let late-game runs have a visible project.
18. Write a one-page **WRITING_GUIDE.md** so new events stay on voice.
19. Normalize background dimensions and do one final art-direction pass (readability of text overlays, consistent palette warmth).

### P4 — long-term health
20. Remove dead code in one cleanup PR: `applyLocationAction`, `applyEventDeltas`, `LOCATION_COPY`, `generate-avatars.js` + `process-portrait.sh` if they are no longer canonical.
21. Move source masters to LFS or an external bucket; document the fetch step for contributors.
22. Reduce UI test runtime by injecting `FADE_MS`/`TOAST_MS` as test globals (set to 0 or 1 in tests).
23. Update stale numbers in README (23 locations, 20 achievements, 371 tests, current coverage).
24. Real-device usability pass: 320 px phone (Chrome + Safari), 768 px tablet, desktop Firefox/Safari/Chrome; keyboard-only and screen-reader (VoiceOver/NVDA) smoke test.

## 9. Bottom line

`secondbarnone` is a good, small game made by people who care about both craft and kindness. The foundation — vanilla ES modules, deterministic simulation, data-driven content, a real test suite, a respectful UX baseline — is genuinely excellent for a project of this size, and most indie web games never get that far.

The remaining work is not glamorous: fix a handful of mechanical bugs the tests cannot see (Sunday prepay, non-persisted event state, a mastery ending that doesn't display, a retreat that doesn't take three days), tighten the balance so rest/rent/events actually pressure the player late into a run, and finish the modal/a11y details. After that, a content pass that makes character arcs legible to the player — rather than just present in the 235-event pool — will turn what is already a charming, meditative half-hour into something memorable.
