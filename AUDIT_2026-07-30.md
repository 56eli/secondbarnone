## 1. Executive verdict

`secondbarnone` is a strong, unusually well-instrumented small web game. Its best decisions are structural: the shipped build is static HTML/CSS/ES modules; most rules and catalogues are DOM-free; one seeded simulator drives the real turn resolver; data integrity is tested over whole catalogues; saves are versioned; art has an explicit two-tier pipeline and byte manifest; and the game has no backend, runtime dependency, account, or operational burden.

The project is substantially healthier than a typical prototype of this size. The writing has a coherent voice, the six-card daily choice is easy to understand, the resource triangle has real pressure, and the current 60-day simulation has a visible skill gradient rather than an immortal optimal strategy.

It is **not yet production-hardened**. Four issues deserve attention before more content is added:

1. **The three-day retreat gives the player another action on its final displayed day.** The browser app and simulator also advance long trips differently, so the balance harness is not simulating the shipped lifecycle.
2. **Zero money is not always lethal.** Out-of-turn spending can take the wallet to exactly zero without a game-over check, after which a profitable location can rescue the run.
3. **The difficulty models use exact preview numbers on fog/rain/snow days even when the player cannot see them.** The 60-day numbers are reproducible, but the strongest models have privileged information on roughly 42% of winter days.
4. **Release control is confused.** GitHub Pages deploys `crazy-branch:/docs`, the repository default is stale/diverged `main`, and the deployment guide instructs maintainers to push `main`.

There are also player-facing content defects (Sato's authoritative sex and shipped pronouns disagree), a duplicate-rent-prepayment charge, unordered/repeating “arc” events, accessibility gaps, and significant documentation/repository drift.

## 2. Project familiarization

### Product

A deterministic narrative resource-management game set in a fictionalized Paris. The player is Léon, balancing a spiritual community against paid bar work. Each playable day is one location choice. Sanity or money reaching zero ends the run; energy creates delayed quadratic sanity and money pressure; reputation gates places and discounts rent; insight buys ten perks and, later, four sanctuary renovations.

Current content:

| Content | Count |
| --- | ---: |
| Locations | 23 across 5 declared districts |
| Hub choices | 6: 2 fixed + 4 deterministic rotating slots |
| Characters | 78 |
| Events | 235, all structurally location-bound |
| Perks | 10 |
| Renovations | 4 |
| Weather types | 9 |
| Festivals | 9 |
| Achievements | 20 |
| Endurance goal | Journey day 60 |
| Mastery condition | Day 100 + 80 reputation + 200 money + 18 locations + bar-streak limit |

### Technical shape

- **Runtime:** static HTML, CSS, and native ES modules; no bundler and no framework.
- **Production code:** 19 JavaScript modules, 8,337 lines including data catalogues; 1,827 CSS lines; 141 HTML lines.
- **Tests:** 6,733 lines across 18 files.
- **Rules:** `docs/js/core/`.
- **Catalogues:** `docs/js/data/`.
- **Presentation:** `docs/js/ui/` and `docs/js/app.js`.
- **Deployment:** GitHub Pages serves `/docs` directly.
- **Persistence:** one `localStorage` save slot, schema v5, plus a settings blob.
- **Randomness:** FNV-derived weather/variance/slot lineups and a persisted Mulberry32 event RNG.
- **Assets:** source masters under `assets/`; deployed WebP/WAV under `docs/assets/`.

The central daily rule is well factored: `computeDayEffects()` produces preview or resolved location effects; `resolveTurn()` applies action, exhaustion, rent, event, travel, achievements, and endings. This is why headless simulation is practical.

## 4. Open findings, prioritized

There is no known remote-code, credential, or save-corruption P0. “P1” below means release-blocking gameplay/operations, not a security emergency.

### P1 — fix before the next stable release

#### P1.1 — The three-day retreat permits two actions on its final displayed day

**Evidence:** `resolveTurn()` marks the turn resolved on starting day `N`, then advances a long trip to `N+2` (`docs/js/core/turn.js:228-266`). In the app, Continue deliberately does **not** call `advanceDay()` for a long trip (`docs/js/app.js:379-395`). `_turnResolvedOnDay` is still `N`, so at the returned hub on journey day `N+2`, `isTurnResolved` is false and another full action is legal.

A direct probe produced:

```text
before:       day 20, unresolved
after trip:  day 22, unresolved, extraDays=2
after bar:   day 22, a second full action resolved
```

That second action also avoids a second Sunday rent because the rent guard already records the displayed day. The copy says three days pass and the hub is framed as a morning decision; getting a second whole-day action on the return date violates both.

**The simulator disagrees with the app:** `playRun()` unconditionally calls `gs.advanceDay()` after every `resolveTurn()` (`scripts/simulate.js:188-190`), including long trips. It therefore resumes on `N+3` and grants an additional night's energy recovery. Between 14% and 27% of 61-day simulated runs visited the retreat at least once depending on model, so this is not a theoretical calibration difference.

**Recommendation:** make “complete turn and enter next playable morning” one core lifecycle operation shared by app and simulator. A three-day action should consume `N`, `N+1`, and `N+2`, then present the next choice on `N+3`; decide and test the intended number of overnight recoveries and rent checks explicitly.

#### P1.2 — Spending to zero bypasses the bankruptcy rule

The stated rule is “money reaching zero ends the run.” That is enforced at the end of `resolveTurn()`, but not for mutations outside a turn.

- `prepayRent()` accepts `money === cost`, subtracts to zero, and does not call `checkGameOver()` (`game-state.js:465-479`).
- `buyRenovation()` does the same (`game-state.js:309-326`).
- Both are free-standing location interactions; the player can return to the hub without consuming the daily action.

On a non-Sunday, a player can spend the last 18 money on prepayment, reach zero while the run remains live, then work the bar and recover to 20. The same escape is possible after an exactly affordable renovation.

**Recommendation:** centralize spend transactions. Either reject a purchase that would leave `money <= 0` or apply it and immediately trigger game over. The UI, core return value, save behavior, and tests must all use the same rule.

#### P1.3 — The difficulty simulator gives models information hidden from players

The UI deliberately applies three preview modes:

- clear/ordinary weather: exact average;
- rain/snow: qualitative `+`/`++`/`-`/`--` bands;
- fog: no effect information.

The simulator always calls `computeDayEffects(..., { preview: true })` and scores the exact numeric bundle (`scripts/simulate.js:45-64, 108-120`). It never calls `previewMode()` or models banded/veiled information. In winter, rain + snow + fog account for about 42% of the weather pool by weight. `concentrates` and `min_maxing` therefore optimize with numbers a human cannot know on a large fraction of the assessed run.

Other fidelity gaps compound this:

- decision randomness and `EventManager` share one RNG instance, so a strategy's random-choice calls alter its later event sequence;
- production seeds events with the run seed, while simulation uses `seed + 7`;
- the simulator buys perks but never buys the four late-game renovations;
- long-trip advancement differs from production (P1.1).

The present table remains a useful regression instrument, but it is not yet a faithful model of the shipped information game.

**Recommendation:** move player-observable preview into a DOM-free helper returning exact/banded/veiled data and require both UI and models to consume it. Give strategy decisions a separate RNG. Add a production-equivalence test for long trips and model renovation spending in horizons beyond day 60.

#### P1.4 — Deployment instructions target the wrong branch

Current remote state:

- repository default branch: `main` at `47abc3f` (“Add files via upload”);
- Pages source: `crazy-branch:/docs` at audited `0376486`;
- `main...crazy-branch`: diverged, with `crazy-branch` 10 commits ahead and 2 behind;
- `DEPLOY.md` and README layout say Pages serves `main:/docs` and instruct pushing `main`.

Following the documented release command would not update the configured Pages source. It could also worsen the already divergent histories.

**Recommendation:** choose one protected canonical branch, make it both default and Pages source, and update deployment docs. Require the green `check` workflow before merge. Do not keep a stale upload snapshot as default while a differently named branch is production.

#### P1.5 — Sato's authoritative identity and shipped copy conflict

`CHARACTER_AND_LOCATION_TEMPLATES.md` marks Sato as **Male** and records the corrected portrait as a Japanese man. Production uses a male portrait, but `characters.js:218` says “whether **she** is right,” and `events.js:1845` says “**She** is not gloating.” This is immediately player-visible on the People and event screens and undercuts the project's own identity-verification art process.

**Recommendation:** owner confirms the canonical identity, then align template, portrait, profile, relationship, and all event copy in one reviewed change. Add structured pronoun/identity metadata if identity consistency will remain a release gate; prose grep tests alone are brittle.

### P2 — important correctness, narrative, accessibility, and process work

#### P2.1 — Repeated rent prepayment charges money without extending cover

`prepayRent(1)` always targets the next Sunday from today and stores it in a `Set`. Calling it again on the same day subtracts the full price again but inserts the same day, buying nothing.

Reproduced from journey day 6 with 90 money:

```text
first payment:  money 72, prepaid [11]
second payment: money 54, prepaid [11]
third payment:  money 36, prepaid [11]
```

The location rerenders after each click, reports that cover exists, but keeps the payment button enabled.

**Recommendation:** target the first unprepaid future Sunday, or disable the action once the offered week is covered. The confirmation should name the covered date.

#### P2.2 — “Multi-beat arcs” are not ordered arcs and events can repeat

Sato, Alex, and Kaden events have minimum-day gates but no prerequisite/sequence gate. On a first late visit, “Tea, Not Terms” can precede Sato's initial offer, Alex's toast can precede his respect/raid beats, and Kaden's buyout can precede the paperwork. Direct seeded probes reproduced each case.

`EventManager` excludes only the last four event IDs. It does not exclude `eventsSeen`, so authored events repeat indefinitely after leaving recent memory. Relationship markers count unique seen IDs and label counts as “First conversation,” “Second beat,” and “Late arc,” regardless of which beat fired (`screens.js:916-932`).

**Recommendation:** distinguish repeatable ambient events from one-shot arc beats. Add data such as `oncePerRun`, `requiresEvents`, and `arcOrder`; pass seen-event state into selection; derive relationship text from named milestones rather than raw counts.

#### P2.3 — Restart does not reset event RNG to the new run seed

`restart()` resets `GameState` and calls `events.reset()`, but `EventManager.reset()` keeps the existing RNG at its current state. For ordinary runs, `GameState.resetGame()` generates a new weather seed while events continue an unrelated old stream. For a shared seeded run, restarting keeps the same weather seed but produces a different event schedule from a fresh boot of that seed.

This violates “same city, same event timing” after Begin Again/Abandon Run.

**Recommendation:** construct/reset the event manager from the reset state's seed, or add an explicit `reseed()` API. Test fresh boot and restart for exact event-scheduler equivalence, not only the allowed 3–6 day range.

#### P2.4 — A later death erases the endurance win

`checkWin()` makes `won` true at day 60. `checkGameOver()` sets `won = false` on any later sanity or money death (`game-state.js:507-520`). A player who reaches day 60 and dies on day 80 gets “The Balance Broke” with no endurance closing note. `reachedGoal` in the simulator is also derived from this non-monotonic flag.

The day-100 mastery flag is not cleared, so the two milestones have inconsistent semantics.

**Recommendation:** make “endurance reached” monotonic. Track current run termination separately from milestones earned, and show both on the summary.

#### P2.5 — The in-game Reduced Motion toggle does not stop particles

The OS media query path stops `startParticles()`, and tests cover that path. The Settings toggle only adds `.reduce-motion`, which shortens CSS animation durations; JavaScript still creates particles and runs an interval every 850 ms. A live jsdom probe found eight particle elements 1.8 s after enabling the in-game toggle.

**Recommendation:** pass the effective preference to `startParticles()` and do not start timers, plus hide `.particles` under the class as defense in depth. Add a test that clicks the actual Settings toggle instead of stubbing `matchMedia`.

#### P2.6 — Portrait modal focus is not trapped

The portrait viewer declares `role="dialog" aria-modal="true"` and focuses its Close button, but its key handler only handles Escape. Tab can move into controls behind the modal. The day-result modal has a focus trap; the portrait modal should use the same controller/primitive.

Related accessibility issues:

- the People panel uses `role=listbox/option` but implements native-button Tab behavior, not the expected arrow-key listbox pattern;
- screen transitions do not place focus on the destination heading or restore focus on ordinary Back navigation;
- footer text `#5f5c56` on `#0a0a12` is about **2.96:1** at 11.5 px, below WCAG AA for normal text.

#### P2.7 — Malformed persisted settings can crash boot

`PreferencesService.load()` spreads arbitrary JSON into preferences and only checks that volume is a number; it does not clamp it. A persisted `{ "sound": true, "volume": 5 }` causes assigning `HTMLAudioElement.volume = 5` to throw `IndexSizeError` during `applyPreferences()`.

**Recommendation:** schema-validate booleans, clamp finite volume to `[0,1]`, and reset invalid data before touching DOM/audio.

#### P2.8 — Result-screen reload remains a full decision rollback

Autosave occurs only after Continue. Seeded event state means reloading and replaying the **same location** gives the same event, which is good. But closing on the result screen restores the morning, allowing a different location choice and therefore a different eligible event pool/outcome. This is ordinary save-scumming, not event rerolling, and current copy overstates “reload replays the exact same scheduled day.”

This may be acceptable for a cozy single-player game. Decide explicitly:

- **accept it:** document autosave as end-of-day and do nothing;
- **close it:** persist a resolved-turn/pending-result record and restore the result modal, which is more implementation work than merely saving immediately.

#### P2.9 — CI does not run the advertised complete quality gate

The active workflow runs tests, asset checks, coverage, and a separate balance report. It does **not** run lint, Prettier check, or TypeScript checkJs. A reviewed patch already exists at `notes/CI_QUALITY_LEGS.patch` but is unapplied.

The test suite is also run once normally and again under coverage. Locally, `npm run check` plus coverage takes roughly two minutes. The balance report runs a third simulation shape (`100 × 200`, hub) while assertions use `300 × 61` hub and `40 × 200` unlocked.

**Recommendation:** add the missing legs; make coverage the authoritative full test run or split fast and browser-like jobs; label every simulation with pool/horizon; publish the exact asserted 60-day table in the job summary.

#### P2.10 — The authoritative character template contradicts the shipped “Oh” character

The template says “Oh” is a misparse of “Ahyeon Oh” and should be removed. Production contains separate `ahyeon` and `oh` profiles, portraits, locations, and three authored events for each; “Oh” is now a coherent standalone poet in the game.

This is no longer a safe mechanical deletion. The owner must choose either to keep the now-developed character and correct the supposedly authoritative template, or merge/remove the character with a deliberate event/location migration.

#### P3.2 — Repository storage and branch hygiene are poor

- `assets/` is about 249 MB; local pack is 298.12 MiB.
- GitHub's repository API reports about 555 MiB across refs.
- `.gitattributes` declares `assets/**` as LFS, but `git lfs ls-files` is empty; masters remain raw blobs.
- There are 31 remote `arena/*` branches, and CI triggers on every branch push.

#### P3.3 — The local server serves WAV with the wrong MIME

#### P3.4 — Asset checks can silently skip visual assertions

## 5. Architecture and code-quality audit

### What is working very well

1. **Rules are mostly independent of presentation.** `core/` and `data/` have no DOM dependency; storage is injectable. A static import-graph probe found no cycle.
2. **Balance constants have a real home.** `core/balance.js` explains intent next to numbers and prevents tuning scavenger hunts.
3. **Catalogues are structural, not convention-only.** Declaring events under location keys and deriving character location names eliminates common dangling-reference bugs.
4. **Determinism is purposeful.** Weather, variance, and slots are pure functions; event scheduler and RNG state are serializable.
5. **Turn reporting is rich.** Resolved deltas, rent, travel rent, event, weather, festival, achievements, and exhaustion are surfaced in one result.
6. **No framework/build dependency.** The deployed source is readable and operationally durable.
7. **Defensive persistence.** Storage failures and malformed save JSON fail softly; v3/v4 migration exists.

### Architectural pressure points

- `GameState` is 951 lines and now owns stats, calendar, rent, perks, renovations, achievements, narrative counters, endings, and persistence. It is coherent today but close to becoming the next monolith. Future arc state and issue #44 should not be added blindly to this class.
- `screens.js` is 1,215 lines and owns generic DOM helpers, portrait modal global state, all screens, character filtering, and result-modal focus. Split by screen only when adding more UI; do not introduce a framework solely for file size.
- `app.js` calls private `gs._statsChanged()` for long trips. That is a clear signal that lifecycle ownership is split incorrectly.
- `el()` supports raw `innerHTML`, but no production caller uses it. Remove the unused escape hatch to keep the XSS surface obviously text-only.
- ESLint treats unused variables and `prefer-const` as warnings. If these are intended gates, use errors or `--max-warnings=0`.
- Content data is frozen at top level but nested effects/unlock objects are not deeply frozen. Internal trusted code does not mutate them; this is low risk.

### Recommended target shape

Do not rewrite. Add three small primitives:

1. **Turn lifecycle service:** resolve action → resolve silent travel → enter next playable morning, shared by UI and simulation.
2. **Transaction API:** spend/prepay/renovate with one bankruptcy rule.
3. **Narrative-event state:** one-shot/repeatable, prerequisites, ordered milestones.

Those changes address the real faults without sacrificing the project's strongest quality: simple readable modules.

## 6. Game design and balance audit

### Core loop

The core choice is excellent: location previews express tradeoffs in a few chips, while weather, rent, energy, and variance create context. The founding pair is readable but insufficient by itself; rest is a costly action rather than a free reset. The quadratic exhaustion curve correctly forgives one hard push and punishes sustained neglect.

Current anchors are internally coherent:

- La Maison Calme: +18 sanity / −8 money / −14 energy.
- Le Dernier Verre: +20 money / −14 sanity / −26 energy.
- Overnight energy: +12.
- Exhaustion below 25 (17 with Second Wind), to −12 sanity and −9 money at zero.
- Rent: 18, +3 every 14 days, cap 48 before discounts.

The 60-day results show the intended skill slope. Death causes also make sense: naive greedy play dies overwhelmingly to money; inattentive play splits sanity and money; stronger models still lose mainly to money as rent escalates.

### Caveats to the measured difficulty

P1.3 means the exact percentages should be treated as regression baselines, not human forecasts. The model named `average` is calibrated by changing an attention probability until it hits a desired band; it is therefore a tuning definition, not independent evidence of average human difficulty.

A supplemental 100-seed, 200-day **hub** run reported:

| Model | Survived horizon (`goal` field) | Mean survival |
| --- | ---: | ---: |
| random | 9% | 44d |
| sometimes | 8% | 71d |
| average | 7% | 71d |
| greedy | 5% | 55d |
| concentrates | 38% | 111d |
| min-maxing | 46% | 128d |

This differs sharply from the documented unlocked-pool stress harness (~88% for engaged models), which is expected because the pools are different. It also reveals that the real hub becomes extremely punishing over a 200-day horizon. However, these numbers inherit all simulator caveats, omit renovation purchases, and use a `won` flag cleared on later death. They should not be promoted to release claims.

### Economy/content observations

Weighted across the full event catalogue, one event averages approximately:

- +2.17 sanity;
- −0.09 money;
- −0.67 energy;
- +0.51 reputation;
- +0.60 insight.

That is a sensible shape: events are emotionally restorative on average but do not erase wallet/energy pressure. Rarity weight is about 8.7%, matching the README's “roughly one in twelve.”

Late-game resources need a human pass. The four renovations cost 125 insight and 140 money total, but the simulator does not buy them. The day-100 mastery condition asks for 200 money while rent has reached its maximum, so mastery feel and attainability are not currently calibrated by a dedicated contract.

### Design recommendations

1. Fix simulation fidelity before changing constants again.
2. Run 6–10 observed playtests: first run to death, informed second run, and seeded comparison. Record why each location was chosen, what previews players believe, and whether fog/bands feel fair.
3. Add a mastery/renovation harness separate from the 60-day contract.
4. Keep only one canonical difficulty unless player research proves a need. The current hard identity is coherent.
5. Do not add more currencies. Reputation and insight already compete for attention; deepen their narrative effects instead.
6. Expose district identity somewhere lightweight (location subtitle or People grouping) or stop marketing five districts as a player-facing system. District data currently has almost no UI expression.

## 7. Narrative, content, and art audit

### Strengths

- The prose is concise, specific, and tonally consistent: warm without becoming consequence-free.
- Every location has residents and a host; every character has at least three local events.
- The 235-event catalogue gives a 60-day run substantial unseen content.
- Event portraits and host small talk make places feel inhabited.
- Locked cards reveal requirements instead of hiding future content.
- The day-one Brian welcome is a strong onboarding beat.
- Character search and grouping make a 78-person cast usable.

### Weaknesses

- Event “arcs” need actual state sequencing (P2.2).
- Relationship marker language overstates what raw event counts prove.
- A favorite location will repeat authored incidents; distinguish ambient/repeatable text from consequential one-shots.
- The protagonist's relationships mostly change in labels, not choices or consequences. The current system is a rich encounter catalogue, not yet a reactive narrative.
- The districts exist primarily in data/tests, not in the player experience.
- Sato and Oh require owner decisions (P1.5/P2.10).
- Open issue #44 proposes starting at 80 reputation, a forced day-2 global Kaden smear to 15, and a “fragile fraud” label until reputation returns to 80. That is a major opening-economy/narrative change, not a cosmetic issue: it needs a global scripted-event path, updated unlock previews, balance reruns, save migration consideration, and careful handling of stigmatizing copy.

### Art

The deployed background sheet is visually cohesive: painterly, muted, recognizably Parisian, and composed with useful dark/quiet space for text. The bright House of Middleway works as a visual reward. Location scenes are one of the game's strongest presentation assets.

Portraits are broadly cohesive in palette and rendering, with expressive environments that communicate role. The full sheet still contains visible legacy variation: circular/oval baked compositions, a few more photographic faces, and occasional generated signage/text artifacts. The active art policy correctly says not to batch-regenerate approved work based on aesthetic guesses. Treat these as an owner-reviewed art-direction inventory before a commercial release, not an automatic replacement backlog.

Provenance is documented as overwhelmingly AI-generated: 1/78 custom character images, 0/78 custom profiles/events, and 0/23 custom location images/descriptions in the template summary. This is not a technical blocker for the current free GitHub Pages build, but it is a commercial/platform/reputation risk. Before Steam, mobile stores, press outreach, or paid distribution, create a per-asset provenance/license ledger and decide whether human authorship replacement is a product goal or merely an aspiration.

The SHA-256 portrait manifest is excellent regression control. It proves bytes, not rights or style; those remain review responsibilities.

## 8. UI/UX and accessibility audit

### Strong work

- Six choices fit the daily decision without a nested map.
- Current date, weather, resources, and insight are continuously visible.
- Money is correctly presented as a wallet total plus comfort bar.
- Exact/banded/veiled previews are a strong way to make weather affect information, not only arithmetic.
- Result modal explains deltas and exceptional costs.
- Touch sizes are generally good; Settings is 44×44 and mobile portrait Close is 44×44.
- Visible focus rings, semantic buttons, labelled meters, alt text, contrast mode, OS reduced-motion support, and local settings are all solid foundations.
- Portrait fallback and lazy hi-res behavior are robust.

### UX risks

- Locked cards can consume several rotating slots. This supports discovery, but a run can present a thin actionable board. Human testing should confirm it reads as anticipation rather than denial.
- Practice purchase estimates are heuristic title tooltips, unavailable or awkward on touch and not necessarily accurate.
- Renovations are only discoverable by returning to one rotating location after day 60/all perks. A soft-win toast should point the player there.
- Share link selection is not the same as a Copy button; add explicit copy feedback if sharing is a promoted feature.
- Settings uses `window.confirm`, which is functional but visually inconsistent and not testable like the custom modal.
- There is no explicit save/export/import. A long mastery run is tied to one browser origin.

### Accessibility actions

1. Reuse one modal primitive with focus trap, Escape policy, focus restoration, and background inertness.
2. Make the People control either a true listbox with arrow/Home/End keys and roving tabindex, or remove listbox roles and keep it as a list of native buttons.
3. Move focus to the new screen heading on navigation and restore it on Back.
4. Fix footer contrast and audit hard-coded colors under high-contrast mode.
5. Make the custom reduced-motion toggle stop JavaScript work, not merely CSS duration.
6. Run NVDA/Firefox or VoiceOver/Safari plus keyboard-only and 200% zoom tests.
7. Add accessible text names to effect chips rather than relying only on emoji pronunciation.

## 9. Performance, security, and privacy

### Performance

The production JavaScript is only about 284 KB unminified, with no runtime dependency. The game should parse quickly on modern devices. Background decode is bounded before transitions; portraits use intrinsic dimensions, lazy loading, and a separate hi tier.

The asset check's “eager” 3.85 MB is actually a conservative **non-hi/non-music deploy tier**, not literal initial network transfer. Browsers initially need HTML/CSS/modules, the hub background, and Léon's portrait; other backgrounds are referenced only when visited and People images are lazy. Rename the metric or add a real browser waterfall budget so release discussions use actual first-load/LCP data.

Headroom under the current conservative 4 MB tier is only 0.15 MB. Either optimize another background/thumbnail batch or consciously move the budget to 4.5–5 MB; do not let the next legitimate content addition make an arbitrary wall the design authority.

The 0.90 MB PCM loop is broad-compatibility but much larger than Opus/AAC alternatives. Keep WAV if simplicity matters; otherwise use `<audio>` sources with a compressed primary and WAV fallback.

### Security/privacy

Risk is low by design:

- no server, database, authentication, cookies, telemetry, ads, or third-party scripts;
- no runtime npm packages;
- no detected secrets;
- no audit vulnerabilities;
- user-facing dynamic text is assigned through `textContent`;
- local server traversal probes were blocked.

Hardening opportunities:

- remove unused `innerHTML` support from `el()`;
- add a restrictive CSP meta policy compatible with module/static assets;
- validate settings and save fields at trust boundaries;
- consider checksums/schema around exported saves if export/import is added.

`window.__game` exposes mutable state. That is acceptable for debugging a local single-player game; do not waste effort on anti-cheat.

## 10. Test and release audit

### Test strengths

The suite is genuinely valuable, not just broad:

- catalogue-wide character/location/event invariants;
- weather season and fringe-month checks;
- deterministic variance properties over long ranges;
- balance survival contracts;
- save migration and event RNG persistence;
- jsdom click-throughs for hub, modal, settings, People, portraits, slots, and share seeds;
- art dimensions, brightness, hashes, orphans, and payload budgets;
- 80% line/branch/function gates with current coverage far above them.

### Important missing tests

Add regressions for every P1/P2 correctness issue, especially:

1. browser-app and simulator next-day equivalence for ordinary/long-trip actions;
2. exactly affordable prepay/renovation bankruptcy;
3. repeat prepayment extension/refusal;
4. model observability under fog/rain/snow;
5. fresh boot vs restart event sequence;
6. monotonic endurance milestone after later death;
7. Settings-toggle reduced motion, not only OS media query;
8. portrait modal Tab containment;
9. malformed settings volume;
10. ordered one-shot arcs;
11. same shared seed reproducing weather, variance, slots, event schedule, and chosen-location event—not weather alone.

### Browser layer

jsdom cannot validate layout, image decoding, CSS media behavior, browser audio policy, focus traversal, WebKit quirks, or real network timing. Add a small Playwright suite rather than replacing jsdom:

- boot fresh and seeded runs;
- play ordinary and long-trip days;
- reload/resume;
- 360×640, 768×1024, and desktop screenshots;
- keyboard navigation and modal focus;
- music toggle without uncaught rejection;
- assert no console/page errors and no 404s.

One Chromium smoke on every PR and a WebKit/Firefox matrix nightly or before release is enough for this project.

### Release process

After choosing the canonical branch:

- make it default and Pages source;
- protect it with required `check` status;
- add lint/format/typecheck to CI;
- update package-lock version with release version;
- create annotated `v2.5.0` (and future) tags/releases—none exist now;
- prune stale session branches after merge;
- verify the actual Pages URL and record deployed SHA in release notes.

## 12. Long-term prospects

The project has excellent durability. Static hosting, no backend, no runtime dependencies, deterministic systems, and a data-driven content pipeline mean it can remain playable with very low maintenance. The code does not need a framework or engine migration.

The main growth risk is not technical scale; it is product coherence. Seventy-eight characters and 235 events create breadth, but relationship depth needs ordered state and consequence. More events without that layer will increase volume faster than meaning. The highest-value content work is therefore not another 100 ambient events—it is making a small number of rival/nemesis/friend arcs remember what happened and change later choices.

The second risk is evidence quality. Simulation is a major advantage, but only if it consumes the same information and lifecycle as the browser. Fixing that contract will make future balancing faster and safer than manual number tweaking.

The third risk is provenance/release discipline. A 10 MB web game should not live in a 500+ MB remote repository with a stale default branch and an undocumented production branch. Cleaning that up will materially improve contributor confidence.

**Bottom line:** keep the architecture, keep the hard readable economy, and keep the restrained tone. Fix lifecycle invariants, make the simulator honest, add real arc state, and establish one release branch. With those changes, `secondbarnone` can move from a very strong experimental web game to a stable, maintainable release without a rewrite.
